## Stable promotion semantics

Repository SemVer changes from `0.2.0-rc.1` to `0.2.0`; Core remains `0.2`; profile remains `repository-filesystem/0.2`. This is not another compatibility migration.

Stable package promotion must:

- change RC-only normative/status wording to stable normative wording;
- preserve all Core/profile `0.1` compatibility artifacts and regression pressure;
- preserve explicit `0.1` → `0.2` migration behavior;
- keep user-facing latest-stable resolution tied to actual GitHub release state;
- use a fresh logical lineage for the stable release branch, not its ref name as identity;
- avoid self-referential operational provenance;
- publish `v0.2.0` only after exact-head full conformance;
- verify `prerelease=false`, `draft=false`, tag target equals exact candidate, and `releases/latest` resolves `v0.2.0`.

Real mount-boundary behavior remains unproven and must remain documented as a limitation; it is not listed as a `v0.2.0` release-blocking milestone gate.
