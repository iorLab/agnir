# Core 0.2 Parallel Continuity design start — 2026-09-02

## Context

The prior `feature/multibranch-continuity` work established an experimental VCS-backed branch-continuity model. Review concluded that the capability is large enough to justify a repository `v0.2.0` release if accepted, and raised the stronger question of whether the backend-neutral semantics should become Agnir Core `0.2` rather than remain only a VCS extension.

## Decision under test

Core `0.2` will be designed around **Parallel Continuity / Continuity Lineage**, not around Git branches.

The design hypothesis is that a single Project may own multiple independently advancing continuity lineages. Backend-specific constructs such as Git refs/worktrees may map to a lineage but must not define the Core abstraction.

## Acceptance evidence required

Core 0.2 adoption requires the same backend-neutral invariants to pass in:

1. a VCS-backed branch/worktree implementation; and
2. a non-VCS transactional namespace/snapshot implementation.

The critical invariants include shared Project identity, lineage-local checkpoint isolation, explicit selection, integration-as-reconciliation, coherent target publication, backend revision receipts not serving as lineage identity, and cross-Project mismatch rejection.

## Versioning direction

If the abstraction survives conformance and real Project validation, intended repository release is `v0.2.0` with Core compatibility `0.2`.

`v1.0.0` remains a separate stability milestone: it requires a durable compatibility contract, tested migration, independent implementation-quality documentation, normative release-blocking conformance, multiple real Projects/surfaces, and no known routine breaking redesign remaining in the Core contract.
