# Agnir v1.0.1 activation-hardening candidate

Date: 2026-09-09 (Project working timezone)

## Trigger

A real downstream Project operation exposed an Agnir Checkpoint Miss: a short repository intent (`提交`) entered an ordinary Git commit path without first executing the Project's already-defined Agnir checkpoint semantics.

The failure did not show that checkpoint semantics were missing. Agnir `1.0.0` already defined commit boundaries and checkpoint no-op behavior. The material product finding was that the activation/operation path could still be bypassed under a short intent when the canonical procedure lived as a section inside a larger README.

Principal-approved direction:

- move Project-specific Executor activation/operation instructions into dedicated root `AGNIR.md`;
- keep `AGENTS.md` locator-only and point it directly to `AGNIR.md`;
- retain the old README heading only as a backward-compatible locator for existing `1.0.0` Projects;
- treat the change as repository/distribution `1.0.1`, with Core `1.0` and `repository-filesystem/1.0` unchanged.

## Implemented candidate

PR: #50 — `Agnir v1.0.1: harden Project activation`

Staging branch: `release/v1.0.1-activation-hardening`

Pre-checkpoint exact candidate head: `ea254e09b999dde8024a76d32e55d5d5fe5868d6`

Material implementation:

1. root `AGNIR.md` is the canonical Executor-facing Project activation + operation surface;
2. root `AGENTS.md` points directly to `AGNIR.md` and remains locator-only;
3. README `## Agnir Project Instructions` is a backward-compatible locator only and is rejected by conformance if it becomes a second full procedure copy;
4. `activation_reference.py` supports the direct `AGNIR.md` route and the legacy `1.0.0` README route only for safe pre-upgrade activation;
5. `agents_merge_reference.py` upgrades the legacy README locator non-destructively while preserving unrelated `AGENTS.md` content;
6. new `operation_dispatch_reference.py` classifies exact repository-context short intents:
   - `commit` / `提交` / `提交代码` -> checkpoint evaluation -> Project-defined pre-commit policy if declared -> commit;
   - `commit and push` / `提交推送` -> checkpoint evaluation -> Project-defined pre-commit policy if declared -> commit -> push -> destination-ref verification;
   - global substring matching is intentionally rejected;
7. checkpoint evaluation is explicitly separated from checkpoint mutation: unchanged durable truth remains no-op;
8. Project-defined verification commands remain Project operation policy rather than Agnir Core semantics;
9. root `SKILL.md` handles fresh install, `1.0.0 -> 1.0.1` compatible activation upgrade, resume, and repair;
10. `VERSIONING.md`, `RELEASE.md`, `RELEASE_MILESTONES.md`, `REPOSITORY_TREE.md`, English/Chinese README surfaces, package tests, self-host gate and stable-release tests are reconciled to the patch model;
11. repository source `VERSION` and `AGNIR.yaml` release metadata are staged at `1.0.1` while `latest_stable` remains `v1.0.0` and applied stable operations provenance remains `1.0.0` until actual publication;
12. `.github/workflows/conformance.yml` accepts `1.0.1` in the 1.0 self-host line and includes a dormant main-only `Publish v1.0.1 stable release` gate. The gate re-runs exact-source self-host/full conformance and verifies immutable `v1.0.0` / `v1.0.0-rc.1` receipts before/after publication.
