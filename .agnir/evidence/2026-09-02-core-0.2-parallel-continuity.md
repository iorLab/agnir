# Core 0.2 Parallel Continuity development evidence — 2026-09-02

## Scope

This evidence records the first backend-neutral Core `0.2` Parallel Continuity design/conformance cycle on `feature/core-0.2-lineage` / draft PR `#5`, stacked on the VCS branch-continuity evidence in draft PR `#4`.

Stable publication remains Agnir repository `v0.1.1`, Core `0.1`, `repository-filesystem/0.1`. The active branch intentionally self-hosts stable Core `0.1` while declaring Core `0.2` only as an experiment.

## Core abstraction pressure

The workstream introduced and tested these generic semantics:

- one Project may own multiple independently advancing Continuity Lineages;
- Project identity is independent of logical lineage identity;
- logical lineage identity is independent of backend selectors/locators and revision receipts;
- ordinary work resolves one lineage from explicit/context/default selection without sibling guessing;
- a selected missing or unbound lineage fails rather than falling back;
- checkpoints are lineage-local;
- integration uses source continuity as reconciliation input, not automatic target truth;
- target Project result + reconciled target continuity publish coherently;
- staged integration becomes stale if target or relevant source advances;
- Core `0.1` → `0.2` is explicit migration, not compatible upgrade.

The normative draft is `spec/AGNIR_CORE_0_2_DRAFT.md`; design rationale is `spec/CORE_0_2_DESIGN.md`.

## Non-VCS evidence

`conformance/sqlite_lineage_reference.py` models logical lineage namespaces in SQLite with no repository, branch, ref, worktree, commit, or VCS merge concept.

SQLite transactions provide coherent publication. Integer generations act as checkpoint receipts/conflict tokens while logical lineage identity remains stable.

Focused pressure covers selection, missing-lineage failure, independent checkpoints, receipt changes without identity changes, staged reconciliation, target/source stale candidate rejection, atomic target publication, source isolation, and cross-Project rejection.

## VCS evidence and abstraction correction

The existing Core `0.1` VCS extension established branch-local continuity and safe staged integration, but deliberately did not define generic lineage identity.

The first Core `0.2` mapping pass initially treated a branch/ref string as the logical lineage identity. Design review exposed a correctness problem: an explicit ref rename would then silently change lineage identity.

The mapping was corrected to:

```text
selected ref/worktree     -> backend selector/binding
logical lineage identity  -> separately resolved durable identity
commit/revision SHA       -> checkpoint receipt/conflict token
```

`conformance/test_core_0_2_vcs_mapping.py` now proves that a ref string can differ from logical identity, an unbound selected ref fails without fallback, a SHA rewrite changes receipt rather than lineage identity, and an explicit ref rename/rebind can preserve logical lineage identity.

`conformance/vcs_lineage_binding_reference.py` / `test_vcs_lineage_binding.py` further prove:

- Agnir-aware branch fork preserves Project identity and inherited baseline but establishes a new logical lineage identity;
- explicit ref rename/rebind preserves logical lineage identity;
- external branch copy carrying a source binding is a mismatch requiring explicit fork-vs-rebind resolution rather than automatic guessing;
- missing binding is explicit failure;
- an independent fork cannot reuse the source logical lineage identity.

## Repository/filesystem 0.2 draft

`profiles/REPOSITORY_FILESYSTEM_0_2_DRAFT.md`, `schemas/agnir-manifest-0.2.schema.json`, `conformance/repository_filesystem_0_2_reference.py`, and `test_repository_filesystem_0_2.py` establish the first concrete Core `0.2` profile candidate.

The manifest requires:

```yaml
agnir:
  version: "0.2"
  discovery_profile: "repository-filesystem/0.2"
project:
  identity: <project-id>
continuity:
  lineage: <logical-lineage-id>
```

The selected root resolves one logical lineage; sibling enumeration remains outside the Core requirement. Stable Core/profile `0.1` discovery explicitly rejects the `0.2` compatibility line rather than silently accepting it.

For optional VCS-backed operation, the profile draft persists logical `continuity.lineage` separately from VCS selector binding. Agnir-aware fork establishes a new logical lineage ID; explicit ref rename updates binding without changing lineage ID; unresolved external binding mismatch requires explicit repair/classification.

## Core 0.1 → 0.2 migration

`spec/CORE_0_1_TO_0_2_MIGRATION.md`, `conformance/core_0_2_migration_reference.py`, and `test_core_0_2_migration.py` define/test the initial migration contract:

- Core-line change without migration authorization remains `AGNIR_UPGRADE_MIGRATION_REQUIRED`;
- the Core `0.1` implicit continuity becomes exactly one initial/default Core `0.2` lineage;
- Project identity, State, Next Actions, Decisions, and Evidence are preserved;
- repeated identical migration is a no-op;
- conflicting second migration cannot silently rebind the initial lineage;
- stale source generation blocks migration publication;
- fresh Core `0.2` resume resolves the preserved initial lineage.

## Self-hosting regressions found and repaired

The stable Core `0.1` self-hosting gate caught two defects introduced during this workstream before new experimental tests could pass:

1. A newly created top-level `docs/` directory violated the repository's established active-structure contract. The fix moved protocol design into `spec/`, conformance planning into `conformance/`, project-wide version/release policy to the root, and removed redundant working/status documents. The stable checker was not weakened.
2. A rewrite of `.agnir/state.md` accidentally dropped the still-valid Project ownership fact `Durable continuity belongs to the Project`. The fix restored the Project-level invariant in branch-local state rather than weakening cold-start conformance.

These failures are evidence that stable self-hosting is acting as a release-safety boundary for experimental Core evolution.

## Current conclusion

The current evidence is sufficient to keep Continuity Lineage as the active Core `0.2` abstraction candidate and to proceed to real-Project validation. It is not yet sufficient to publish Core `0.2` stable.

Before `v0.2.0`, at minimum one explicitly authorized real Project should exercise the concrete model through genuine parallel work, independent checkpoints, selector/binding behavior, and target reconciliation. The preferred first consumer remains Svif because it already consumes Agnir `0.1` through a defined Continuity Provider boundary.

PR `#4` / `#5` integration into authoritative `main` must still obey the target-publication invariant: final `main` continuity must be reconciled before the revision that advances `main`; do not knowingly publish an intermediate `main` revision containing feature-local continuity truth.
