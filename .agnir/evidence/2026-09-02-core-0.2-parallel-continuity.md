# Core 0.2 Parallel Continuity development evidence — 2026-09-02

## Scope

This evidence records the backend-neutral Core `0.2` Parallel Continuity design/conformance cycle on `feature/core-0.2-lineage` / draft PR `#5`, stacked on the VCS branch-continuity evidence in draft PR `#4`.

Stable publication remains Agnir repository `v0.1.1`, Core `0.1`, `repository-filesystem/0.1`. The active branch intentionally self-hosts stable Core `0.1` while declaring Core `0.2` only as an experiment.

## Core abstraction pressure

The workstream introduced and tested these generic semantics:

- one Project may own multiple independently advancing Continuity Lineages;
- Project identity is independent of logical lineage identity;
- logical lineage identity is independent of backend selectors/locators and revision receipts;
- ordinary work resolves one lineage from explicit/context/default selection without sibling guessing;
- a selected missing or unbound lineage fails rather than falling back;
- checkpoints are lineage-local;
- integration uses source continuity as reconciliation input, not automatic target truth;
- target Project result + reconciled target continuity publish coherently;
- staged integration becomes stale if target or relevant source advances;
- Core `0.1` → `0.2` is explicit migration, not compatible upgrade.

The normative draft is `spec/AGNIR_CORE_0_2_DRAFT.md`; design rationale is `spec/CORE_0_2_DESIGN.md`.

## Non-VCS evidence

`conformance/sqlite_lineage_reference.py` models logical lineage namespaces in SQLite with no repository, branch, ref, worktree, commit, or VCS merge concept.

SQLite transactions provide coherent publication. Integer generations act as checkpoint receipts/conflict tokens while logical lineage identity remains stable.

Focused pressure covers selection, missing-lineage failure, independent checkpoints, receipt changes without identity changes, staged reconciliation, target/source stale candidate rejection, atomic target publication, source isolation, and cross-Project rejection.

## VCS evidence and abstraction correction

The existing Core `0.1` VCS extension established branch-local continuity and safe staged integration, but deliberately did not define generic lineage identity.

The first Core `0.2` mapping pass briefly treated a branch/ref string as the logical lineage identity. Design review exposed a correctness problem: an explicit ref rename would then silently change lineage identity.

The corrected mapping is:

```text
selected ref/worktree     -> backend selector/binding
logical lineage identity  -> separately resolved durable identity
commit/revision SHA       -> checkpoint receipt/conflict token
```

`conformance/test_core_0_2_vcs_mapping.py` proves selector string != logical identity, unbound selected ref failure without fallback, SHA rewrite as receipt change rather than identity change, and explicit ref rename/rebinding that preserves logical lineage identity.

`conformance/vcs_lineage_binding_reference.py` / `test_vcs_lineage_binding.py` further prove:

- Agnir-aware branch fork preserves Project identity and inherited baseline but establishes a new logical lineage identity;
- explicit ref rename/rebind preserves logical lineage identity;
- external branch copy carrying a source/stale binding is a mismatch requiring explicit fork-vs-rebind resolution rather than guessing;
- missing binding is explicit failure;
- an independent fork cannot silently reuse the source logical lineage identity.

## Repository/filesystem 0.2 draft

`profiles/REPOSITORY_FILESYSTEM_0_2_DRAFT.md`, `schemas/agnir-manifest-0.2.schema.json`, `conformance/repository_filesystem_0_2_reference.py`, and `test_repository_filesystem_0_2.py` establish the concrete Core `0.2` repository profile candidate.

The selected Project root requires Core/profile `0.2`, the durable Project identity, one logical `continuity.lineage`, and the lineage's memory locators. Sibling enumeration remains outside the Core requirement. Stable Core/profile `0.1` discovery explicitly rejects the `0.2` compatibility line rather than silently accepting it.

For optional VCS-backed operation, logical `continuity.lineage` is distinct from selector binding. Agnir-aware fork establishes a new logical lineage ID; explicit selector rename updates binding without changing the lineage ID; unresolved external binding mismatch requires explicit repair/classification.

## Core 0.1 → 0.2 migration semantics

`spec/CORE_0_1_TO_0_2_MIGRATION.md`, `conformance/core_0_2_migration_reference.py`, and `test_core_0_2_migration.py` define/test the storage-neutral migration contract:

- Core-line change without migration authorization remains `AGNIR_UPGRADE_MIGRATION_REQUIRED`;
- the Core `0.1` implicit continuity becomes exactly one initial/default Core `0.2` lineage;
- Project identity, State, Next Actions, Decisions, and Evidence are preserved;
- repeated identical migration is a no-op;
- conflicting second migration cannot silently rebind the initial lineage;
- stale source generation blocks migration publication;
- fresh Core `0.2` resume resolves the preserved initial lineage.

## Concrete repository/filesystem migration

`conformance/repository_filesystem_0_2_migration_reference.py` and `conformance/test_repository_filesystem_0_2_migration.py` extend the semantic migration into a concrete `AGNIR.yaml` transition.

The implementation deliberately stages before publishing:

1. resolve/validate the Core/profile `0.1` source and Project identity;
2. require explicit migration authorization and a non-empty initial logical lineage identity;
3. capture a digest of the authoritative source manifest;
4. construct the Core/profile `0.2` manifest with `continuity.lineage` while preserving Project identity and memory locators;
5. reject publication if the source manifest changed after staging;
6. write to a temporary manifest, flush/fsync, and atomically replace `AGNIR.yaml`;
7. fresh-resolve the Project through `repository-filesystem/0.2` and verify expected Project/lineage identity;
8. treat repeated identical migration as a no-op and conflicting lineage rebinding as migration conflict.

This closes the gap between storage-neutral migration semantics and an executable repository/filesystem migration path suitable for real consumer validation.

## Self-hosting regressions found and repaired

The stable Core `0.1` self-hosting gate caught two defects introduced during this workstream before experimental work was accepted:

1. a newly created top-level `docs/` directory violated the repository's established active-structure contract. Protocol design was moved into `spec/`, conformance planning into `conformance/`, and repository-wide release/version policy to root files. The stable checker was not weakened;
2. a rewrite of `.agnir/state.md` accidentally dropped the still-valid Project ownership fact `Durable continuity belongs to the Project`. The fact was restored in branch-local state rather than weakening cold-start conformance.

These failures are evidence that stable self-hosting acts as a release-safety boundary for experimental Core evolution.

## Current conclusion

The synthetic/backend/profile/migration evidence is sufficient to keep Continuity Lineage as the active Core `0.2` abstraction candidate and proceed to real-Project validation. It is not yet sufficient to publish Core `0.2` stable.

The next release-blocking validation should be an explicitly authorized real Project. The preferred first consumer is Svif because it already consumes Agnir through a defined Continuity Provider boundary.

Required real evidence: explicit Core/profile `0.1`→`0.2` migration, two genuinely divergent logical lineages, independent checkpoints, selector/binding behavior, staged target reconciliation/publication, and fresh resume of both source/target after integration.

PR `#4` / `#5` integration into authoritative Agnir `main` must still obey the target-publication invariant: final `main` continuity must be reconciled before the revision that advances `main`; do not knowingly publish an intermediate `main` revision containing feature-local continuity truth.
